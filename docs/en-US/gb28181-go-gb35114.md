# GB 35114-2017 A-level security (SM crypto): device and platform roles

[GB 35114-2017](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=B7F5589329EF98B32F0EB8ACEC341C81)
(security requirements for public-security video-surveillance networks)
layers Chinese national-cryptography (SM) protection on top of GB/T 28181
signaling: SM2 certificate mutual authentication, SM3 signaling integrity,
SM4 session-key agreement. In government / enterprise / GB-Tiered-Protection
procurement documents, "GB35114 / A-level / SM2·SM3·SM4" are hard keywords —
**public open-source implementations that cover the A-level handshake on
BOTH sides are rare**; most stop at digest authentication or implement one
role only. gb28181-go ships both, and both are opt-in: without the
`gb35114` build tag the default build carries zero SM dependencies.

This is the deep-dive manual: handshake wire format, wiring for both
roles, the configurable ambiguities, operational notes. For the quick
start see the [README](../../README.md#gb35114-a-level-security-v040-device--v050-platform-opt-in).

## A-level only, by design

GB 35114 defines levels A/B/C: B and C additionally require secured
signaling plus **SVAC (GB/T 25724) encrypted audio/video**, and SVAC is a
hardware codec ecosystem — a pure-software library cannot implement it,
and there would be nothing to interoperate with. The library therefore
implements **A-level only** (the `security35114` package doc says the
same); B/C are explicitly off the roadmap. What A-level covers here:

| A-level capability | Where it lands |
|---|---|
| SM2 certificate authentication (device → platform) | device-side `Authenticator`, replacing REGISTER Digest |
| Platform authentication (platform → device, `Bidirection`) | device verifies `sign2`; platform-side `Platform` signs it |
| Session-key agreement (VKEK, SM2 envelope) | both sides, DER C1‖C3‖C2 envelope |
| Subsequent-signaling integrity (keyed-SM3 `Note` header) | both sides: device signs outgoing, platform verifies; since v0.7.0 the device also verifies platform-initiated requests |
| SM4 stream-cipher capability announcement | `A:SM2;H:SM3;S:SM4/OFB/PKCS5;SI:SM3-SM2` |

## The handshake wire format (both roles share one picture)

```
REGISTER   (Authorization: Capability …, cnonce?)     device → platform
401        (WWW-Authenticate: … random1="…")          platform → device   Challenge
REGISTER   (Authorization: Unidirection|Bidirection
            … sign1="…")                              device → platform   VerifyRegister
200 OK     (SecurityInfo: cryptkey [, sign2])         platform → device
```

- `sign1` = SM2 signature over random2‖random1‖serverID with the device
  key — proof the device holds the FDWSF certificate's private key;
- `cryptkey` = the VKEK sealed under the device certificate's public key
  (SM2 envelope) — only the real device can open it; every later request
  carries `Note: Digest nonce="…",algorithm=SM3` keyed by the VKEK;
- `sign2` (`Bidirection` only) = the platform's signature over the same
  randoms — proof to the device that the platform is not a man in the
  middle.

After the handshake every outgoing device request (keepalive, message
acknowledgements, …) carries `Note` automatically, and the platform
verifies each one. Three knobs — `RandomEncoding`, `Sign2Order`,
`VKEKEncoding` — cover the three points where the standard text and real
captures disagree; defaults follow observed captures (`RandomEncoding`)
and the standard text (`Sign2Order`). When an interop partner reads the
payloads differently, turn the knobs first — do not fork the code.

## Device-side wiring (UAC)

```go
// go build -tags gb35114
import sec "github.com/mickeyzzc/gb28181-go/security35114"

auth, err := sec.New(sec.Options{
    Device:       devIdentity,     // sec.LoadIdentityFromFiles(certPEM, keyPEM)
    PlatformCert: platCert,        // sec.LoadCertificate(certPEM) — verifies sign2
    DeviceID:     "34020000001320000001",
    ServerID:     "34020000002000000001",
})
cfg.RegisterAuthenticator = auth   // installed = the REGISTER lifecycle switches to 35114
```

With `RegisterAuthenticator` installed, the REGISTER Digest dance is fully
replaced by Capability → 401 → sign1 → SecurityInfo, and later requests
(keepalive, …) carry `Note` automatically. Downstream integrity
(platform → device requests carrying `Note`) is governed by
`device.Config.IncomingNotePolicy`: `Reject` by default (bad signature
draws 403), `Warn` and `Off` exist for rollout; `Note`-less requests keep
passing, so SM and Digest platforms mix freely. The `Date` freshness
window is ±5 minutes.

## Platform-side wiring (UAS)

```go
// go build -tags gb35114
plat35114, err := sec.NewPlatform(sec.PlatformConfig{
    ServerID:    "34020000002000000001",
    Identity:    platIdentity,   // platform SM2 signing cert+key — signs sign2
    DeviceCerts: map[string]*smx509.Certificate{deviceID: devCert},
})
sipCfg.RegisterAuthenticator = plat35114 // platform/sip.Config; the Digest path is untouched
```

`platform/sip` routes by the REGISTER Authorization scheme: `Digest`
requests keep flowing through password authentication, while
`Capability`/`Unidirection`/`Bidirection` go to `security35114.Platform`
and the 200 OK carries `SecurityInfo`. Digest and SM devices register
into the same platform concurrently.

Operational properties of the platform side (what multi-device fleets
rely on):

- **Sessions keyed by device ID**, safe for concurrent use;
- **Replay rejection** — an Authorization echoing a `random1` that is not
  the pending challenge is refused (`ErrChallengeMismatch`), mapped to 4xx;
- **Retransmission idempotence** — SIP-over-UDP REGISTER retransmissions
  get the cached 200 OK;
- **VKEK grace** — while a device re-registers, the previous VKEK keeps
  verifying until the new handshake completes, so live `Note`s don't drop;
- **Two certificate sources** — pre-provisioned `DeviceCerts`, or trust
  the Capability `cnonce` announcement (first-touch enrollment; pair it
  with out-of-band fingerprint checking).

## Certificate provisioning

The GB 35114 certificate system (FDWSF device certificates, platform
certificate, CA chain) is an out-of-band process by standard; this
library does not issue or revoke certificates. Two entry points:

- Out-of-band provisioning (recommended): device certificates into the
  platform's `DeviceCerts`, the platform certificate into the device's
  `Options.PlatformCert`;
- `cnonce` announcement: the device sets `Options.IncludeDeviceCert =
  true` and carries its certificate PEM in the Capability — useful when
  pre-provisioning is impossible during interop. **In production always
  pair this with fingerprint verification**, otherwise the announcement
  channel is equivalent to no authentication.

## Build and dependencies

```sh
go build -tags gb35114 ./...
```

SM2/SM3 come from [emmansun/gmsm](https://github.com/emmansun/gmsm)
(pure Go, GM/T 0015-2012 SM2 X.509 certificates) — imported only under
the `gb35114` tag; default builds stay dependency-light. CI runs the
test suite for the tagged build as well.

## How this is verified (not "should work")

- **Golden wire formats**: byte-pinned tests for the three authentication
  headers (Authorization / WWW-Authenticate / SecurityInfo) and `Note`;
- **End-to-end loopback**: a real `device.Server` (device-side
  Authenticator) against a real `platform/sip.Server` (`Platform`) —
  handshake, VKEK agreement, and the first keepalive's `Note` verification
  all under real SM2/SM3;
- **Downstream verification**: the accept/reject matrix for `Note`-carrying
  platform requests at the device has its own tests.

## Selection cheat sheet

- "Video networking + SM-crypto compliance" (tiered protection, government
  intranets): this library — A-level, both roles, GB/T 28181
  2011/2016/2022 signaling, one dependency.
- The peer is a GB35114 platform/device: interoperate directly; when the
  handshake misbehaves, check the three knobs above first.
- Levels B/C (SVAC media encryption) are out of scope — they require the
  hardware SVAC ecosystem.
- Only transport security is needed, not 35114: use SIPS (TLS signaling,
  `-transport tls`, see the [interop lab](gb28181-go-interop-lab.md)) —
  no need for SM crypto.
